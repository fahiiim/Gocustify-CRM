# Message Tab: Backend Fix Requirements


This document covers only issues that need backend changes. The source audit is `../MOBILE_MESSAGE_TAB_AUDIT.md` (2026-11-22); the mobile fixes are in `MESSAGE_TAB_MOBILE_FIX_REPORT.md`.


No backend code, schema or data was changed.


**Evidence.** The "Probe" references are throwaway pytest files run against the backend in-process on the project's own mongomock fixtures (`app/tests/conftest.py`), with every provider faked:


- `audit_probe_test.py`: P1–P8, from the audit.
- `mobile_fix_probe_test.py`: F1–F5, re-run after the mobile fixes.


Neither file is in any repository.


Paths are relative to `Mabdel Backend/app/`.

## Critical


### BE-1: A "group" conversation can pull users from another business into a thread


| Field | Detail |
|---|---|
| Audit IDs | J2 (BF1) |
| Severity | **Critical**: authorization / privacy |
| Current behaviour | `POST /api/v1/smartflow/conversations` with `type:"group"` and any user IDs in `member_ids` returns 201. The thread appears in those users' inboxes, and they can read and post in it. |
| Expected | The same reachability rule as for `type:"direct"`: a colleague in the same organization, or a person saved as a contact. Groups should be created through `/groups`. |
| Confirmed root cause | `ConversationCoreMixin.create_conversation` (`services/smartflow/conversation/core.py:79-84`) calls `_assert_members_share_organization` only when `conversation_type == "direct"`. `_get_accessible_conversation` path 4 (`services/smartflow/_base_mixins/access.py:102`) then grants access to anyone listed in `member_ids`. |
| Evidence | Probe P8: `direct` with a stranger's ID → 403. `group` → **201**. Thread in the stranger's inbox: `True`. Stranger `GET …/messages` → **200**. |
| Mobile usage | After this fix pass the mobile app no longer calls this. `GroupChatScreen` used to fall back to `POST /conversations {type:"group"}`, and that fallback was removed. The endpoint is still open to any API client. |
| Endpoint | `POST /api/v1/smartflow/conversations` (`api/v1/endpoints/smartflow/conversations.py:176-184`) |
| Data | `conversations.member_ids`, `conversations.organization_id` |
| Why mobile cannot fix it | This is server-side authorization. |
| Required change | On the public endpoint, either reject `type:"group"` (create groups only through `POST /groups`), or run `_assert_members_share_organization` on every member that is a valid user ObjectId, whatever the type. Stamp `organization_id`. Add a regression test equivalent to P8. |
| Dependent mobile workflows | None functionally. This is about data exposure in every user's inbox. |
| Priority / blocks production | P0. **Blocks production readiness.** |

## High


### BE-2: Outbound messages trust the client's `platform` and `contact_id`


| Field | Detail |
|---|---|
| Audit IDs | C3 (BF2). Also affects D1 and G9. |
| Severity | High (integrity: a reply is stored as "sent" without being delivered) |
| Current behaviour | `create_message` stores `platform` and `contact_id` exactly as the client sends them. Two cases fail: <br>1. `platform:"ai"` in a WhatsApp thread is stored as `sent` and **never delivered**, because `_deliver_outbound` returns True for `ai`. <br>2. The correct platform without `contact_id` fails WhatsApp, Messenger, Instagram and email delivery ("no … address"). |
| Expected | For a customer conversation, the server takes the channel and recipient from the conversation, and rejects a mismatched platform. |
| Confirmed root cause | `messages.py:56-57` (`"contact_id": payload.get("contact_id")`, `"platform": payload["platform"]`). `delivery.py:39-40` skips `ai`/`internal`. `delivery.py:349-358` needs `contact_id`. |
| Evidence | Probe P1: the old mobile body gave `sent` / `ai` with 0 provider calls. No `contact_id` gave `failed`. With `contact_id` the message was delivered. After the mobile fix, probe F1 shows WhatsApp delivered and probe F2 shows SMS delivered. |
| Mobile usage | Fixed on mobile: it now sends the conversation's platform and `contact_id` (`src/utils/chatThread.js` `buildOutgoingRequest`). The **website still omits `contact_id`** (`Mabdel Website/src/pages/UnifiedConversations.jsx:312`), so its WhatsApp, Messenger, Instagram and email replies remain affected. |
| Endpoints | `POST /api/v1/smartflow/messages`, `POST /api/v1/smartflow/messages/{id}/reply` |
| Service | `ConversationMessagesMixin.create_message`, `reply_to_message`, `ConversationDeliveryMixin._finalize_outbound_delivery` |
| Data | `conversations.platform`, `conversations.contact_id`, `messages.status` |
| Why mobile alone is not enough | The server must not let any client turn a customer reply into an undelivered message that reports success. Other clients (the website) still omit `contact_id`. |
| Required change | In `create_message`, when the conversation is a customer conversation (`_is_customer_conversation`): <br>1. Default `contact_id` to `conversation["contact_id"]`. <br>2. Reject (400) or override a `platform` that differs from `conversation["platform"]`. |
| Dependent mobile workflows | Customer replies (text, image, voice), delivery ticks, failure display |
| Priority / blocks production | P0–P1. **Blocks production** for the website; defence in depth for mobile. |


### BE-3: The conversation WebSocket ignores the `messages:view` permission


| Field | Detail |
|---|---|
| Audit IDs | J3 (BF3) |
| Current behaviour | A member restricted by RBAC to `invoices:view` gets 403 on REST, but `WS /ws/conversations/{id}` accepts them and streams messages. |
| Evidence | Probe P6: REST 403, socket `ACCEPTED connected`. |
| Endpoint | `WS /api/v1/smartflow/ws/conversations/{conversation_id}` (`api/v1/endpoints/smartflow/conversations.py:28-49`). The inbox socket already checks, at `:91-95`. |

| Priority / blocks production | P0. **Blocks production** (permission bypass). |


### BE-4: Group members picked from contacts never gain access


| Field | Detail |
|---|---|
| Audit IDs | J4, K12, K17 (BF4) |
| Current behaviour | Both the mobile and website group member pickers list **contacts** (`Mabdel Website/src/pages/Groups.jsx:232`, mobile `CreateGroupScreen`/`GroupSettingScreen`), so `member_ids` hold contact IDs. Every access check matches **user IDs** (`services/smartflow/conversation/groups.py:56`, `_base_mixins/access.py:102`). Only the owner, plus colleagues added by user ID, can open the group. |
| Evidence | Code trace (a sub-review, confirmed against the code). Not probed at runtime. |
| Endpoints | `POST /api/v1/smartflow/groups`, `POST /groups/{id}/members`, `PATCH /groups/{id}` |

| Why mobile cannot fix it | The mobile app sends the same contact IDs as the website. Mapping a contact to a platform user is server knowledge (`_resolve_group_member_user_id` already does it for RBAC). |
| Required change | When members are added, resolve each contact to its linked user and store user IDs in the group conversation's `member_ids`. Alternatively, accept user IDs from a teammate picker (`GET /conversations/assignees` already lists teammates) and document that contract. |
| Dependent mobile workflows | Group chat for non-owners: open, read, send, leave |
| Priority / blocks production | P1. Blocks group messaging for everyone except the owner. |

|---|---|
| Audit IDs | G9 (BF6) |

| Priority / blocks production | P1. |

## Original behavior


Mobile sends a transcript and `requested_fields_only: true` to `POST /api/v1/smartflow/ai/workflow-prefill`. The response travels through `_extract_workflow_prefill_with_ai`, `_sanitize_ai_prefill`, and `_sanitize_ai_value` before the app receives it. An in-process probe executed the checked-out parsing functions on synthetic inputs without calling the provider or database.


| Input | Observed backend result | Impact |
|---|---|---|
| Model value `"1,5"` | `15.0` | Can change invoice quantity, unit price or tax, lease rent or deposit, or meeting reminder. |
| Model value `"1.234,50"` | `1.2345` | Can turn 1,234.50 into roughly 1.23 after money rounding. |
| Model value `"1,,5"` | `15.0` | Malformed input becomes a plausible number. |
| Rent due day `"4.5"`, `"32"`, or `"invalid"` | `4`, `31`, or `1` respectively | Fractional and invalid days are truncated, clamped, or replaced. This is a shared backend field. The current mobile voice mapper does not bind it. |
| Legacy transcript price `$1,5` or `$1.234,50` | `15.0` or `1.23` respectively | The fallback uses separate regular expressions and comma deletion. |
| Legacy transcript `1.5 hours at $10 each` | Quantity `5`, unit price `10.0` | The integer-only regex matches the trailing part of the fractional quantity. |
| Lease draft prompt `Rent is $1,5 per month`, `Rent is $1.234,50 per month`, or `Deposit is $200` | The fallback returns 1,500, 123, or 20,000 cents respectively | Localized rent is misparsed and a deposit-only prompt can be treated as rent. |


Finite JSON numbers retain their value in the current sanitizer. The probe also verified that zero survives and boolean, `NaN`, and infinity are rejected by the floating-point sanitizer. Existing endpoint fixtures cover JSON numbers. They do not prove correctness for localized model strings.


## Backend changes


| Priority | Location | Required change |
|---|---|---|
| High | `app/services/smartflow/_base_mixins/workflow_prefill.py`, `_extract_workflow_prefill_with_ai`, `_coerce_float`, and `_sanitize_ai_prefill` | Explicitly request JSON numbers with no currency symbols or locale separators. Validate the actual response independently of the prompt. Accept finite JSON numbers and parse numeric strings only when their format determines a single value. Parse `"1,5"` as 1.5 and both `"1,234.50"` and `"1.234,50"` as 1234.50. Reject malformed separators and strings such as `"1,234"` when no explicit numeric format disambiguates them. Use decimal parsing internally and keep JSON numbers in the response. |
| High | `workflow_prefill.py`, `_sanitize_ai_value` and invoice line-item validation | Enforce field constraints before returning the patch. Quantity must be positive and can be fractional. Unit price, rent and deposit must be nonnegative. Tax must be 0–100. Reminder minutes must be an integer from 0–10,080. Rent due day must be an integer from 1–31. Preserve valid zeroes and omit invalid scalar fields from the patch. For an invoice list with an explicitly invalid quantity or price, withhold the unsafe list update while preserving other valid fields.
